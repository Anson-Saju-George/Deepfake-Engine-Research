## 1. Orientation

This repo is a deepfake-detection research pipeline (image + raw-video) built on `timm` backbones, a custom protocol-aware `DataLoader` builder (`data/dataloader.py`), and per-run artifact folders under `train/`. It has produced 22 completed experiments (5 image, 17 video), already tabulated in `docs/Results.md`/`docs/REVISION_AUDIT.md`. Image detection is near-saturated (best F1 0.9863); raw video is materially harder (best F1 0.7841), and the repo's own `books/08_model_evaluation.md` treats that gap as a headline finding, not a failure to explain away. A third code layer exists at `docs/code/*.py` — an orphaned (zero-import) reference implementation of identity-disjoint splits, video-level-AUC metrics, SBI augmentation, and perturbation robustness tests, written the same day as `docs/RESEARCH_PLAN.md`, the 8-week paper-submission programme this refactor is meant to serve. The active trainers currently **cannot be imported** (`NameError` at module load — `contextlib`/`sys` used but not imported), meaning the 22 completed runs almost certainly predate a refactor that broke this, or were never re-verified after it landed. `books/` is a disciplined, self-aware methodology narrative (protocol separation, identity-aware splits, train-only balancing, honest reporting of what didn't work — FFmpeg QSV, Decord, focal loss) that is largely accurate against the code; where it isn't, `docs/Current-Status.md` §10 and §9 already flag the specific contradictions (`VID-ST-07..12` "reserved" language vs. completed runs under those IDs). `docs/code/splits.py`, `metrics.py`, `sbi.py`, `perturbations.py` are not aspirational filler — each maps almost 1:1 onto a Phase-5 rewrite need and is largely reusable as-is; the work is integration, not invention. `.gitignore` already excludes `*.pth`, `Weights.zip`, `models/`, `temp/` and none of them are git-tracked (verified via `git ls-files`), which materially de-risks the storage-cleanup tasks below — there is no git-history rewrite required for any of them.

This summary does not contradict `docs/Current-Status.md`; it restates its five headline findings in the framing this refactor needs.

### T0 — Hygiene and storage reclamation

- **Scope**: verify `Weights.zip` contents are byte-identical to what's under `train/`; delete `Weights.zip` only after that verification is reported; report (not act on) `temp/` (12 GB) and duplicate `final_*.pth` reclaimable space; propose `.gitignore` additions.

- **Risk**: **Low** for the deletion itself — `Weights.zip` is git-untracked (§2), so deletion is not a git-history event and is trivially recoverable from `train/`/`models/` if the verification step is done correctly first. The actual risk is in the verification step being sloppy — a wrong byte-comparison method (e.g. trusting file size alone rather than a hash) could let a genuinely different archived file get silently discarded. Mitigation: use a cryptographic hash (`sha256`) per-file, not size/mtime, and require zero mismatches before proceeding.
- **Acceptance tests**: (a) a generated verification report listing every file inside `Weights.zip` (via `zipfile.ZipFile.namelist()` + per-entry hash) matched against a same-hash file under `train/`, with an explicit PASS/FAIL per entry and an overall PASS/FAIL; (b) `Weights.zip` no longer exists at repo root after deletion; (c) `git status` shows no change (confirms it was untracked, so nothing to commit).
- **Estimated effort**: verification script ~1 hr to write + run (hashing 16.9 GiB will dominate wall-clock, likely 15–40 min depending on disk speed); report review + deletion: minutes.
- **Dependencies**: none. Can run first, independently of T1–T5.

### T1 — Central data pipeline (`data/dataloader.py` and satellites)

This is the largest and highest-risk task; the plan below breaks it into sub-deliverables so it does **not** have to be approved or executed as one atomic unit.

- **T1.0 — Blast-radius quantification (must run and be reported before any dataloader code changes)**: re-run `train/video/validate_video_dataset.py` (already functional, confirmed §2) across all three video dataset scopes, both `single` and `sequence` modes, and cross-reference the resulting `bad_video_suspects.txt` against every completed run's training window (derived from `train.log`/`config.json` mtimes per run directory) to estimate how many synthetic zero-tensor samples plausibly entered each of the 17 completed video runs. This is diagnostic only — it does not change behavior, and its output is required input to the Open Decision in §7 ("decode-failure default").
- **T1.1 — Dataset registry** (`data/dataset_registry.py`): convert `DATASET_CONFIG` (data/dataloader.py:105-126) into declarative entries: root, on-disk structure, per-class label map, identity-extraction strategy name, and a `role` field (`train_only` / `test_only` / `either`) so `docs/RESEARCH_PLAN.md`'s "Dataset roles (never violate)" table (Celeb-DF/DFDC test-only, FF++ train-only, etc.) becomes a machine-checked constraint instead of a documentation promise. New datasets (DFDC-Preview, DeeperForensics-1.0, later KoDF/DeepSpeak/ForgeryNet) become new dict entries, not new `if cfg["structure"] == ...` branches.
- **T1.2 — Explicit identity derivation** (`data/identity.py`): replace `get_identity`'s silent full-path fallback (data/dataloader.py:513-523) with per-dataset regex extractors modeled on `docs/code/splits.py:ffpp_identity`/`celebdf_identity` (already correct, reusable as-is), plus a **hard failure** (not a silent per-file identity) when a filename in a *known* dataset doesn't match its declared pattern. Unknown-dataset files should raise at registry-build time, not quietly get folded into split logic as "identities of one."
- **T1.3 — Split logic replacement**: wire `docs/code/splits.py`'s `deterministic_split`, `assign_splits`, `check_leakage`, `balance_by_clip_sampling`, `lomo_configs` into `DatasetBuilder.prepare_records` (data/dataloader.py:1046-1096), per the integration point the prior audit already identified. `check_leakage()` becomes a mandatory, non-bypassable call before any split is returned to a trainer.
- **T1.4 — `n_clips` / asymmetric clip expansion**: extend the `VideoRecord`-equivalent sample representation so a single video can expand to N training samples (real videos get more clips, fake fewer, or vice versa, per `docs/code/splits.py:balance_by_clip_sampling`) without discarding any video — this changes `DatasetBuilder.get_loaders`'s sample-list construction, not `DeepFakeDataset` itself.
- **T1.5 — Stride parameter**: add `stride` to `_contiguous_indices` → `DeepFakeDataset.__init__` → `DatasetBuilder.get_loaders`, default `stride=1` (preserves current behavior exactly when unset), target config `seq_len=16, stride=4`.
- **T1.6 — Multi-clip inference**: add an eval-time sampler that draws N clips per video and returns per-clip predictions keyed by video ID, matching the `{video_id: [clip_score, ...]}` shape `docs/code/metrics.py:aggregate_clips` expects.
- **T1.7 — Decode-failure policy**: replace the unconditional `torch.zeros(...)` fallback (data/dataloader.py:474-478) with a configurable policy (`drop` / `raise` / `zero_with_flag`), default **not** the current silent-zero behavior (see Open Decision §7) — every dropped/flagged sample logged and counted, not just video decode failures as today (image/frame failures currently aren't logged at all — confirmed, `_log_bad_video` is only called from `dtype=="video"` branches).
- **T1.8 — Root configuration**: `DatasetBuilder(root=...)` gains an env-var/config default instead of the hardcoded `"datasets"` literal (data/dataloader.py:485, 668) — kept backward compatible (same default value) so existing invocations don't change behavior.
- **T1.9 — Caching layer**: design (this task) + stub interface for a pre-extracted face-crop cache with validity checks (hash of source video + extraction params → cache key), reusing the existing `FRAME_DATASET_SOURCES`/`dtype="frame"` convention as the on-disk storage mechanism. Full implementation of the extractor itself is **T3's** job, not T1's — T1 only needs to define the *read* contract `DatasetBuilder` will consume.
- **Files touched**: `data/dataloader.py` (heavily refactored — see §6 breaking-changes note), new files `data/dataset_registry.py`, `data/identity.py`, `data/splits.py` (promoted), `data/clip_sampling.py`, `data/decode_policy.py`, `data/cache.py`. `docs/code/splits.py` becomes a thin re-export shim or is deleted after promotion (decision needed — see §7).

A subtle behavioral change here (e.g., a different random shuffle order under the same seed, a changed default `val_ratio`) can silently make new runs non-comparable to the 22 completed ones without anyone noticing, which is exactly the failure mode this whole engagement exists to prevent.

## 6. Breaking Changes

Stated plainly, per the prompt's explicit requirement — anything below invalidates or reinterprets the 22 completed runs' comparability to future runs:

1. **Any decode-failure policy change (T1.7) that stops silently zero-filling failed video decodes** changes what a "sample" meant during training for every one of the 17 completed video runs that used the current dataloader. The 22 completed runs' reported numbers do not change retroactively (they're frozen in `final_summary.json`/`test_evaluation.json`), but **no future run under a new decode policy is directly comparable to them without re-stating that the corpus composition assumption changed**. This must be called out explicitly in any paper table that spans pre- and post-refactor runs.
2. **Any label-convention resolution (§7) that changes which class the active eval layer treats as positive** changes the *meaning* of every previously-reported F1/precision/recall number, even though the underlying accuracy/AUC numbers (convention-invariant, confirmed §2) do not change. If the resolved convention differs from what `train/eval_predictions_common.py` currently uses (real=1=positive), **every existing F1/precision/recall value in `docs/Results.md`/`docs/REVISION_AUDIT.md` needs a "which convention" annotation or a recomputation**, not a silent reinterpretation.
3. **Identity-derivation hard-failure (T1.2)** may cause datasets that previously split "successfully" (via the silent full-path fallback) to now fail loudly if their filenames don't match a declared pattern. This is a deliberate, desired breaking change (the whole point is to stop silently defeating identity-aware splitting), but it means **some future run attempt may simply refuse to start** where the old code would have proceeded — this needs to be flagged as an intentional new failure mode, not a bug, when it's first hit.
4. **Asymmetric clip sampling / `n_clips` expansion (T1.4)** changes the effective per-video weighting in training — this is the explicit purpose of the change, but it means **any future run using `n_clips`-based balancing is not directly comparable to the 22 completed runs**, which used simple oversampling (`_apply_class_balance`, whole-sample repetition) instead. Both are legitimate balancing strategies; they are not the same strategy, and result differences between them should be attributed to the balancing-method change, not treated as a pure architecture/hyperparameter effect.
5. **Stride > 1 clips (T1.5) are not directly comparable to the completed runs' stride-1 clips** — a 16-frame/stride-4 clip spans a longer temporal window (64 frames of coverage) than an 8-frame or 12-frame stride-1 clip from the same video. Any paper claim about "longer context helped" must control for this, not conflate window length with clip length.
6. **`TemporalConvHead`/`ConvLSTMHead`/`ConvLSTMCell` extraction (T2b)** must be verified bit-identical (acceptance test T2b-c) specifically *because* a silent behavioral drift here would invalidate the already-published `docs/MODEL_COMPLEXITY.md` numbers without any visible symptom — this is exactly the "silent bug worse than a crash" scenario the prompt's ROLE section warns about.
7. **`Weights.zip` deletion (T0) and `models/` deletion (T5) do not affect result comparability** — they are pure storage artifacts, not part of the experimental pipeline. Included here only to state explicitly that they are *not* breaking changes, since their scale (tens of GB) might otherwise suggest they are.

## 8. Risk Register

What could silently corrupt results, and the guard for each.

| Risk | Silent failure mode | Guard |
|---|---|---|
| Split-order change under the same seed | `random.Random(seed)` shuffles produce a *different* train/val/test partition than the current code, even with the identical seed value, because the input iteration order changed (e.g., dict ordering, `Path.rglob` filesystem-order differences across T1's registry refactor) | Acceptance test T1-(c): new-code split **counts** must match the recorded `split_summary.json` for at least one completed run's exact config, before any other T1 change is considered done. If counts match, order may still differ — for full parity, also spot-check that the recorded `identity` set assigned to `test` doesn't change for the identity-aware protocol (video). |
| Metrics rewire silently changes which class is positive | A "successful" T2a/T2b metrics rewire that inverts F1/precision/recall without anyone noticing, because AUC/accuracy — the numbers most likely to get a casual glance — don't change | Acceptance test T2a-(c)/T2b equivalent: re-evaluate an already-completed run and diff every reported metric, not just accuracy, against `docs/Results.md`. Any F1/precision/recall delta beyond floating-point tolerance is a stop-ship signal, not a "huh, interesting" note. |
| `TemporalConvHead`/etc. extraction changes numerics | Moving a class to a shared module while accidentally changing a default argument, initialization order, or `nn.Module` submodule registration order (which can affect `state_dict()` key names and therefore checkpoint-loading compatibility) | Acceptance test T2b-(c): params/FLOPs must match `docs/MODEL_COMPLEXITY.md` exactly. Additionally (not yet in the test list above, adding here): confirm an **existing checkpoint** (e.g. `VID-TMP-07`'s ConvNeXt-LSTM `best.pth`) still loads via `load_state_dict` with `strict=True` after the extraction — a silent key-name change would break checkpoint compatibility without breaking the import or the smoke test. |
